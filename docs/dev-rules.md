# 개발 규칙

> 모든 구현(웹 2D 검증, Unity, 서버)에 공통으로 적용한다. 엔진별 세부는 9장.
> 설계 문서: [design/](design/) · 구조: [design/structure.md](design/structure.md) · 검증: [design/verification.md](design/verification.md)

목표 네 가지:
1. **캡슐화** — 모듈 안을 바꿔도 밖이 모른다.
2. **이식성** — 규칙 코드는 엔진·플랫폼·서비스를 모른다.
3. **확장성** — 새 기능은 기존 코드를 고치지 않고 **추가**로 붙인다.
4. **부작용 방지** — 한 곳을 고쳐서 다른 곳이 깨지지 않는다. 깨지면 테스트가 먼저 잡는다.

---

## 1. 모듈과 의존 방향

- 모듈 구성은 [structure.md](design/structure.md) 2장을 따른다.
- **의존은 한 방향**: 화면(UI·View) → 규칙 모듈(Battle·Progression·Campaign·Economy·Online …) → Data. 거꾸로 참조하지 않는다.
- **규칙 모듈끼리 직접 호출 최소화**: 다른 모듈이 필요하면 **공개된 경계(인터페이스·입출력 객체)**만 쓴다. 예: 전투는 `BattleSetup`을 받고 `BattleResult`를 낼 뿐, 경제·포로 모듈을 모른다.
- 모듈마다 **공개 API를 작게** 둔다. 나머지는 내부(비공개)로 숨긴다.
- 순환 의존 금지. 빌드 단계에서 막는다 (Unity는 어셈블리 정의로 강제).

## 2. 캡슐화 규칙

| 규칙 | 내용 |
|---|---|
| 상태는 주인만 바꾼다 | 각 상태(장수, 부대, 지갑, 전투 상태 …)는 **소유 모듈만** 바꾼다. 다른 모듈은 요청하거나 이벤트로 알린다 |
| 전역 상태 금지 | 정적 싱글톤·전역 변수로 상태를 공유하지 않는다. 필요한 것은 생성자로 받는다 (의존성 주입). 조립은 시작 지점 한 곳(`GameBootstrap`)에서만 |
| 정의 데이터는 읽기 전용 | 데이터 파일에서 읽은 정의(병종·진형·스킬 …)는 불변 객체. 실행 중 바뀌는 값은 별도 상태 객체 |
| 이벤트로 알리기 | 모듈 간 "무슨 일이 일어났다"는 이벤트로 알린다. 받는 쪽이 늘어나도 보내는 쪽은 안 바뀐다 |
| 한 클래스 한 책임 | 시스템 하나 = 클래스 하나 ([structure.md](design/structure.md) 3.2) |

## 3. 이식성 규칙

| 규칙 | 내용 |
|---|---|
| 규칙 코드는 엔진 무관 | 전투·성장·경제·포로·고용 규칙에 엔진 타입(Unity의 `MonoBehaviour`, `Vector3` 등)을 쓰지 않는다. 자체 값 타입을 쓴다 |
| 결정적 계산 | 전투 규칙은 같은 입력이면 **어느 기기·서버에서든** 같은 결과. 기기마다 다를 수 있는 계산 금지 (구현별 수학 방식은 9장) |
| 무작위는 한 곳 | 무작위 값은 **시드를 받은 난수 서비스**에서만 얻는다. 엔진·언어 기본 난수를 규칙 코드에서 직접 쓰지 않는다 |
| 시간은 한 곳 | 현재 시각은 `ITimeProvider`에서만 얻는다 (기기 시계 → 서버 시간 교체 대비) |
| 데이터 키는 영문 id | 한국어 이름을 키로 쓰지 않는다. 화면 문구는 테마 문자열 ([theme.md](design/theme.md)) |
| 데이터 형식 | JSON + 스키마 + **버전 번호**. 형식이 바뀌면 변환기(마이그레이션)를 함께 만든다 |

## 4. 외부 서비스 적용 유무

로그인·결제·광고·서버·분석·푸시 같은 외부 서비스는 **켜고 끄기 쉽게** 분리한다.

| 규칙 | 내용 |
|---|---|
| 경계 뒤에 숨긴다 | 서비스마다 인터페이스(`IAuthService`, `IStoreService`, `IAdService` …). 게임 코드는 인터페이스만 안다 |
| 구현은 갈아 끼운다 | 서비스마다 **실제 구현 / 테스트용 가짜 / 끔(아무것도 안 하는 구현)**을 둔다 |
| 켜고 끄기는 설정으로 | 어떤 구현을 쓸지는 **서비스 설정 파일**(빌드 환경별: 개발 / 테스트 / 출시)로 정한다. 코드 수정 없이 바꾼다 |
| 서비스가 없어도 동작 | 서비스가 꺼지거나 응답이 없어도 게임은 멈추지 않는다 (광고 없음 → 광고 보상 버튼 숨김, 서버 없음 → 오프라인 안내 등) |
| SDK는 구현부에만 | 외부 SDK(광고·결제·백엔드)는 그 구현 클래스 안에서만 참조한다. 다른 코드에 SDK 타입이 새어 나가지 않는다 |
| 규칙 스위치와 구분 | **규칙 스위치**(게임 규칙 켜고 끄기, [battle.md](design/content/battle.md) 2.20)와 **서비스 설정**(외부 서비스 켜고 끄기)은 다른 파일로 둔다 |

## 5. 확장성 규칙

| 규칙 | 내용 |
|---|---|
| 추가로 확장 | 새 명령·행동·스킬 효과·승리 조건·전장 유형·탭·로그인 수단은 **구현을 추가하고 등록표에 등록**한다. 기존 분기문(`switch`)에 끼워 넣지 않는다 |
| 수치는 데이터 | 코드에 숫자를 박지 않는다 (`balance.json` 등). 예외: 0, 1 같은 자명한 값 |
| 문구는 데이터 | 화면 문구를 코드에 쓰지 않는다 (테마 문자열 표) |
| 규칙 스위치 | 웬만한 규칙은 켜고 끌 수 있게 만든다. 꺼진 규칙은 계산·화면에서 빠지고 다른 규칙에 영향이 없다 |
| 덮어쓰기 순서 | 공통 기본값 → 스텝 → 규칙 세트. 이 순서를 한 곳(`BalanceResolver` 등)에서만 처리한다 |

## 6. 부작용 방지

### 6.1 테스트

| 테스트 | 내용 | 언제 |
|---|---|---|
| 단위 테스트 | 시스템·계산기마다 | 커밋 전 |
| 규칙 테스트 (R) | [verification.md](design/verification.md)의 규칙 예시. 현재 데이터 값으로 계산 | 커밋 전 |
| 수치 테스트 (N) | 예시 수치로 고정 | 커밋 전 |
| 기준 전투 | 정답 파일과 같은 결과인지 | 커밋 전 |
| 데이터 검사 | 스키마, 참조 id 존재, 상성표 대칭(R-14), 상점 상품 플레이 경로(R-30) 등 | 데이터 변경 시 |
| 스위치 조합 | 주요 규칙 스위치를 켠/끈 상태 모두 | 자동 (CI) |
| 밸런스 시뮬레이션 | 절대 강자 탐지, 난이도 승률 | 밸런스 변경 시 |

- **모든 테스트는 자동으로 돈다** (CI: push·PR마다). 실패하면 합치지 않는다.
- 버그를 고칠 때는 **그 버그를 재현하는 테스트를 먼저** 추가한다.

### 6.2 변경 관리

| 규칙 | 내용 |
|---|---|
| 작게 나눠 바꾸기 | 한 번의 변경(PR)은 한 가지 목적. 기능 추가와 리팩터링을 섞지 않는다 |
| 경계 변경은 신중히 | 모듈 공개 API·입출력 객체·데이터 형식을 바꾸면 버전을 올리고, 쓰는 곳 전부와 테스트를 같이 고친다 |
| 규칙 변경 = 문서 변경 | 게임 규칙을 바꾸면 **설계 문서와 verification.md를 같은 변경에서** 고친다 |
| 오류는 숨기지 않는다 | 예외를 조용히 삼키지 않는다. 개발 빌드는 바로 멈추고, 출시 빌드는 기록 후 안전하게 복구 |
| 세이브 호환 | 세이브 형식이 바뀌면 이전 세이브 변환기와 테스트를 함께 추가 |

## 7. Git 규칙

| 규칙 | 내용 |
|---|---|
| 기본 브랜치 보호 | 기본 브랜치에 직접 push하지 않는다. 작업 브랜치 → PR → 테스트 통과 → 합치기 |
| 커밋 메시지 | 무엇을 왜 바꿨는지 한 줄 요약 + 필요하면 본문 |
| 태그 | 설계 `design-vX`, 구현 `impl-<엔진>-vX.Y`. 출시 빌드는 둘을 함께 기록 |
| 큰 파일 | 3D 모델·텍스처·사운드는 Git LFS |
| 비밀 정보 | API 키·인증서·결제 비밀값은 저장소에 넣지 않는다 (환경 설정·비밀 저장소 사용) |

## 8. 완료 기준 (Definition of Done)

하나의 작업이 끝났다고 말하려면:
- [ ] 설계 문서·verification.md와 일치한다 (다르면 문서를 먼저 고쳤다)
- [ ] 새 수치·문구는 데이터에 있다
- [ ] 관련 테스트가 추가·갱신되었고 전부 통과한다
- [ ] 외부 서비스는 인터페이스 뒤에 있고, 꺼도 동작한다
- [ ] 의존 방향을 어기지 않는다 (빌드에서 확인)
- [ ] 리뷰를 받았다 (또는 자체 점검 목록을 확인했다)

## 9. 엔진별 세부

### 9.1 Unity

| 규칙 | 내용 |
|---|---|
| 어셈블리 | 모듈마다 어셈블리 정의(asmdef). 규칙 어셈블리는 `UnityEngine` 참조 금지 (설정으로 강제) |
| 결정적 수학 | 전투 규칙은 고정소수점 또는 기기 간 결과가 같은 수학 라이브러리 ([impl/unity/decisions.md](impl/unity/decisions.md)) |
| 화면 코드 | `MonoBehaviour`는 화면·입력에만. 규칙 상태를 직접 들고 있지 않는다 |
| 성능 | 매 프레임 실행되는 곳에서 메모리 할당 최소화, 병사·이펙트는 풀링 |
| SDK | 광고·결제·백엔드 SDK는 해당 구현 어셈블리에만 |
| 테스트 | 규칙은 에디터 없이 도는 단위 테스트 (Unity 테스트 프레임워크 EditMode 또는 일반 .NET 테스트) |

### 9.2 웹 2D 검증

- 규칙 모듈 구조와 이름을 Unity 설계와 1:1로 맞춘다 (나중에 옮기기 쉽게).
- 데이터 JSON은 그대로 공유한다.
- 화면은 검증용이므로 꾸미지 않는다.
